`.devcontainer/deploy-keys.sh` inventorie automatiquement les dépôts à servir — `origin` du hub, `bundles/upstreams.yaml`, remotes de `bases/*/` — et génère la paire de clés manquante pour chacun. Mais l'étape suivante, l'enregistrement de la clé publique côté GitHub, reste manuelle : le script affiche l'URL `https://github.com/<owner>/<repo>/settings/keys/new` et la clé à coller, et il faut relancer le script après l'avoir fait. C'est reproductible à chaque base ajoutée : sur ce dépôt, quatre bases (`el2d-blueway`, `el2d-referentiel`, `okf-hub-feedback`, `phoenix-blueway`) ont chacune nécessité ce même aller-retour manuel vers l'interface GitHub.

Attendu : l'idée du hub étant de faciliter la gestion des bases de connaissances, ajouter une base ne devrait pas demander une action manuelle par dépôt sur un site tiers — surtout pour un geste répété à chaque nouvelle base, potentiellement par des opérateurs qui ne connaissent pas le mécanisme de deploy keys.

Pistes techniques observées, à arbitrer plutôt qu'à implémenter directement (golden rule 5) :

- `gh` (GitHub CLI) est déjà présent dans l'image du conteneur (`gh version 2.98.0`, vérifié dans ce conteneur), sans être déclaré en feature devcontainer. `gh repo deploy-key add <fichier.pub> --repo <owner>/<repo> --title "…" [--allow-write]` peut enregistrer une deploy key par appel API, si l'opérateur s'est authentifié une fois (`gh auth login`, ou un token dans l'environnement). Ça ramènerait le geste manuel de « un clic par dépôt » à « une authentification par machine », déjà nécessaire ailleurs (identité git de `git-identity.env`).
- Alternative plus proche du script actuel : appel direct à l'API REST GitHub (`POST /repos/{owner}/{repo}/keys`) avec un token détenant la permission Administration sur le dépôt (PAT fine-grained scopé aux seuls dépôts du hub, jamais un token de compte large).
- Point à trancher avant toute implémentation, conformément au § 1 de la spec du hub sur les principes remontés au propriétaire : faire porter au conteneur un token capable d'écrire des deploy keys élargit la surface de ce que peut faire une session compromise, ce que la migration vers des deploy keys par dépôt (commit d5cc03d) visait justement à réduire. Le compromis (automatisation vs. surface d'un token d'administration) mérite d'être arbitré explicitly, pas juste codé.

Contournement actuel : suivre la procédure documentée dans `README.md` (§ deploy keys) et relancer `deploy-keys.sh` après chaque enregistrement — fonctionne, mais suppose que l'opérateur sache ce qu'est une deploy key et ait les droits admin sur le dépôt GitHub cible.
